1. Problem Definition & Bridge Pattern Rationale

In object-oriented design, when an abstraction has multiple possible implementations, using naive inheritance tightly couples them. For instance, subclassing shapes directly by rendering type (e.g., VectorCircle, RasterCircle, VectorSquare, RasterSquare) causes a combinatorial explosion of classes (M × N, where M is the number of shapes and N is the number of rendering backends). Adding a third renderer requires creating subclasses for every shape.

The Bridge Pattern decouples this system into two orthogonal hierarchies linked via object composition:

  • Abstraction Dimension: High-level domain entities (Shape, Circle, Square) holding domain attributes (id, radius, side).
  • Implementation Dimension: Low-level graphics operations (Renderer interface, VectorRenderer, RasterRenderer, AsciiRenderer).

By replacing inheritance with composition (the bridge reference protected Renderer renderer), the class count scales linearly as M + N. Crucially, it allows runtime replacement of the renderer on the same shape object via setImplementation(...) without altering object identity or domain data.

3. Five Annotated Clean Code Excerpts

The codebase reflects Clean Code best practices (Martin, 2008), maximizing maintainability and clarity:

Excerpt 1: Separation of Responsibilities (Single Responsibility Principle)
// In src/Circle.java @Override public String execute() { return renderer.renderCircle(radius); }
Benefit: Circle is strictly responsible for managing circle data (radius), while drawing operations (pixels, vectors, or ASCII) are isolated in Renderer implementations.
Excerpt 2: Meaningful Names
// In src/Renderer.java and src/VectorRenderer.java public interface Renderer { String renderCircle(int radius); String renderSquare(int side); }
Benefit: Descriptive names (renderCircle, VectorRenderer, setImplementation) clearly communicate intent without ambiguous abbreviations or explanatory comments.
Excerpt 3: Small Focused Methods
// In src/Shape.java public void setImplementation(Renderer renderer) { if (renderer == null) { throw new IllegalArgumentException("Renderer cannot be null"); } this.renderer = renderer; }
Benefit: The method is concise (6 lines), performs one atomic task with guard validation, has no side effects, and is trivial to test.
Excerpt 4: Avoidance of Duplication (DRY Principle)
// In src/Shape.java public abstract class Shape { protected final String id; protected Renderer renderer; public Shape(String id, Renderer renderer) { this.id = id; this.renderer = renderer; } }
Benefit: Common attributes (id, renderer) and implementation-swapping logic are centralized in the abstract base class rather than duplicated across Circle and Square.
Excerpt 5: Encapsulation of State
// In src/Circle.java public class Circle extends Shape { private final int radius; // ... public int getRadius() { return radius; } }
Benefit: Field radius is private final, preserving internal invariants from unauthorized mutation. External classes can only inspect it via getRadius().

5. Trade-offs & Comparison with Adapter Pattern

Specific Trade-off of the Bridge Pattern

The primary trade-off of Bridge is increased architectural complexity and indirection. Introducing separate interfaces and delegation layers requires more classes and indirect method calls. In simpler applications with only a single implementation that will never change, Bridge introduces unnecessary overhead.

Comparative Analysis: Bridge vs. Adapter

Dimension Bridge Pattern Adapter Pattern
Primary Intent Decouples an abstraction from its implementation so both vary independently. Converts an incompatible interface of an existing class into a target interface expected by clients.
Design Phase Designed up-front during system architecture before classes are implemented. Applied after the fact (retrospectively) to integrate legacy or third-party classes.
Structure Two parallel, independent class hierarchies connected via an interface reference. A single wrapper class adapting an existing adaptee to a target client interface.
Relationship Collaboration between an Abstraction and an Implementor interface. Translation layer between two otherwise incompatible interfaces.
